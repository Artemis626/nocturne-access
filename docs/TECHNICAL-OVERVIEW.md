# Nocturne Access: technical overview

**Spoiler warning:** this document names places, bosses and events of the game that some players may consider spoilers.

## About this document

- **Status of the project:** work in progress. The source code is public (since 26 Nov 2026); a packaged release will come once the project owner has finished the whole game with it at least once. The optional Labyrinth of Amala is done and the playthrough has reached the final dungeon.
- **Source code:** https://github.com/Artemis626/nocturne-access
- **Version described:** development build 0.0.179, 21 November 2026.
- **Authorship:** this document was generated by an AI agent (Claude, by Anthropic), the agent that writes the mod's code, from the source code and the project's engineering records. Testing, design decisions and every choice of spoken wording are by the project owner, a low-vision NVDA user.
- **Format:** written for screen readers: one heading per topic, short lists, no tables.

## What the mod is

- A screen-reader accessibility mod for Shin Megami Tensei III Nocturne HD Remaster, Steam version for PC.
- It speaks through NVDA. Other screen readers are planned for later.
- It speaks only the game's own text: text written to the screen, the game's message engine, and the game's data tables. There is no OCR. Numbers the game draws as images are read from game data.
- License: GPL-3.0.

## Platform and toolchain

- **Game engine:** Unity 2019.4, IL2CPP build.
- **Mod loader:** MelonLoader 0.6.1. The mod targets .NET 6 and uses HarmonyX and Il2CppInterop.
- **Hooks:** Harmony patches, applied one at a time and each logged, so one failing hook cannot stop the others.
- **Research:** read-only static analysis of the game's code library (`GameAssembly.dll`). The DRM-protected executable is never inspected.
- **Offline game data:** asset bundles, field scripts, door tables, area files and localization tables are read with the project's own tools. They are used to classify events, find the game's own words, and plan routes before testing in game.

## Architecture

### Text and speech

- A single hook on the game's text-writing path. Each text component is classified once by its position in the interface tree and handed to the reader that owns it.
- Blank writes are dropped, and identical rewrites never count as new activity.
- A background speech queue with interrupt and protected lines, plus an ordering layer so a question is always spoken before its options.
- Short synthesised sound cues (earcons), each with its own switch in the configuration.

### Readers

- **Story:** dialogue pages with the speaker, choices, prompts, location banners.
- **Menus:**
  - every game menu;
  - save and load lists, configuration, name entry;
  - status pages, item and skill lists, the level-up skill choice, fusion skill inheritance;
  - a key-help key that reads the screen's own button guide, then the mod's keys for that screen.
- **Shops and services:** the Junk Shop (prices, owned counts, sums, rows the party cannot afford), the Fountain of Life (fees), the Terminal and Amala Link travel, Rag's Jewelry trades.
- **Cathedral of Shadows:** both fusion tables with results, in the game's own localized words, and the Demon Compendium, with View including summon cost, and Register.

### Battle

- **Turns:** the acting unit, Press Turns full and half, enemy actions.
- **Results of each action:**
  - damage, healing, weakness, critical hits;
  - Block and Missed, from the game's own word popups;
  - "No effect" when an ailment or instant-kill skill changes nothing.
- **Statuses:** said as they start and end, in the game's own help wording.
- **Menus and picks:**
  - skill costs and elements, read from the game's tables;
  - affinities once Analyze has shown them;
  - target picks, including dead allies;
  - the Summon list with each demon's level, HP and MP.
- **After the battle:** results with spoils, including after bosses.
- **Any time:** status keys for each side, and a battle log of the last turns.

## Navigation

### Data the mod reads from the game

- **Player and place:** position, facing, area and field.
- **Geometry:** every collision polygon of the loaded area, including moving objects and the game's own collision switches.
- **Event volumes:** doors, story events, actions, warps, with their boxes and facings.
- **The game's door table:** destinations and movement types (door, touch warp, ladder, jump, floor warp).
- **Other sources:**
  - place-name floor pads, NPC and item box tables, story flags;
  - the field scripts, dry-run with the live flags to know what each event does before it is visited.

### The walking map

- 30-unit cells, with up to 8 floor heights per cell.
- Floors and walls are chosen by the game's own polygon attributes; trigger-only polygons are not walls.
- Steps, railings, ramps and floor seams follow the game's own hit test: radius 45, walls tested 35 above the floor, steps up to 55, lift floors up to 75.
- Moves reach every floor layer within a step, in both directions.
- The overworld map has its own rule set.
- Dijkstra search with wall-distance cost and a turn penalty. Story events count as soft costs, so routes avoid triggering them.
- Moves the game refuses during a walk are learned and routed around.

### Points of interest and movement

- **The points list:**
  - doors, with room name, kind and learned destination;
  - exits, ladders, escalators and warps;
  - people, demons, item boxes (opened or not), and events with the game's own first line;
  - a fixed map order with filters.
- **Auto-walk and directions:** auto-walk to any point, or spoken directions on demand. Walking is driven only through the game's own input checks at normal speed, so the game's collision, doors and events stay in charge. Positions are never written.
- **Doors gone through:** remembered per save file, written only when the game saves.
- **The way on:** a key that names the next point of the main route. It is used only in the hardest dungeons, where getting through is impossible without the game's map. Its data comes from published walkthroughs matched to the game's door tables, area files and scripts; the sources are credited in the README.
- **First person:** the game's locked first-person view is answered in memory only, and the save is never changed. An optional grid snap keeps the game's own controls. Wall, opening and door cues speak only changes and never block input.

### Puzzles and minigames

- **The Obelisk time puzzle:** the next tile is derived from the field script's variables, matched to published solutions.
- **The Labyrinth of Amala falling minigame:** an autopilot steers through the game's own input. A key hands control back at any time.
- **Changed content:** a few parts that depend on reacting to the screen faster than speech or sound can tell are changed for accessibility, each listed in the README with its configuration switch where it has one. Bosses are never skipped.

## Diagnostics and quality checks

- Every session log is archived.
- On-demand dumps:
  - all visible text;
  - the navigation state: collision, volumes, door table, the walking map drawn as text;
  - battle data.
- Offline copies of the walking map rebuild reachability from any saved dump. Every rule change is checked against all recorded areas before it ships, and nothing that worked may get worse.
